title: Docs contract
description: How a page is added, where it is linked, and what makes the site build fail.
---

The site is Docusaurus 3 with the content at the repository root: `website/` holds the config, the
sidebar and the theme, and `docs.path: '../docs'` points the site at `docs/`. The pages render at
`/`, so a file at `docs/guides/testing.md` is served at `/guides/testing`.

## Add a page

1. Create `docs/<section>/<page>.md` with front matter:

   ```markdown
   ---
   title: Installing the CLI
   description: One sentence a search result can show.
   ---
   ```

   `title` renders the heading — do not repeat it as `# …` in the body. `description` is required.
   `slug` is used on the landing page only (`docs/index.md` has `slug: /`); everywhere else the file
   path is the URL.

2. Add it to `website/sidebars.ts` in the same change. One explicit entry per page, in reading order:
   the sidebar is not autogenerated, so an orphan is visible and a rename does not reorder anything.

3. Link it from a page that already exists, or from the README's index table (which is generated, see
   below).

## Links

| From | To another page | To a repository file outside `docs/` | To a website |
|---|---|---|---|
| a docs page | relative, with extension: `./installation.md`, `../reference/flags.md` | `https://github.com/managingwp/gridpane-nginx-marketing-params/blob/main/PATH` | plain URL |
| `README.md` | absolute site URL | `./scripts/x.sh` (GitHub resolves it) | plain URL |

Never start a link with `/`: the site is served from `/gridpane-nginx-marketing-params/`, so an
absolute path 404s. In-page anchors (`#section`) are fine and are checked at build time.

## MDX

Files are MDX, not plain Markdown: `{` starts an expression and `<` starts a tag, outside a code
fence or inline code. Put such text in backticks (`` `<site>` ``, `` `{name}` ``) or escape it. Two
guards make this loud rather than quiet:

- `onBrokenLinks`, `onBrokenAnchors` and `markdown.hooks.onBrokenMarkdownLinks` are all `throw`, so a
  dead link or anchor fails the build.

## Generated pages

Two artefacts are generated and must not be edited by hand — the next run reverts the change.

| Artefact | Generated by | Marker pair |
|---|---|---|
| `docs/history/changelog.md` | `website/scripts/gen-changelog.sh` | `BEGIN/END GENERATED: changelog` |
| the README index table | `website/scripts/gen-readme-index.mjs` | `BEGIN/END docs-index` |

```bash
cd website && npm run gen
```

The changelog excludes its own file from `git log`, so running the generator twice leaves the file
byte-identical.

## Build, serve and check

```bash
cd website
npm install
npm run start     # local dev server
npm run build     # production build into website/build/
npm run typecheck
```

The gate runs the build and then the checks:

```bash
bash scripts/check-docs-site.sh --site website --docs docs --repo-root .
```

It verifies the config's guards, exact `@docusaurus/*` pins and a committed lockfile, front matter on
every page, one sidebar entry per page, relative links, the README line budget and its marker pair,
and the search plugin settings. Exit status is the verdict.

## Deployment

`.github/workflows/docs.yml` builds and checks every pull request and deploys `main` to GitHub Pages.
`website` is uploaded as the Pages artifact, so no `.nojekyll` is needed.

One-time manual step, once, in the repository settings: **Settings → Pages → Source: GitHub Actions**.
Until it is set, the deploy job fails with "Get Pages site failed" while the build job still passes.
The site is served from `https://managingwp.github.io/gridpane-nginx-marketing-params/`
(`url` and `baseUrl` in `website/docusaurus.config.ts`).
